# CLAUDE.md

## Conventions

- Commits and PR titles follow **Conventional Commits** (`feat(cv):`, `fix:`, `chore(deps):`, `ci:`,
  ...); PRs are squash-merged, so the PR title becomes the commit subject.
- The PR description says why and what changed. Keep it in sync with the branch after every push.
- Nothing repo-specific goes in agent memory: repo facts belong in the repo's docs, agent guidance here.

## Engineering Philosophy

- **Pathfinder**: leave it better than you found it.
- **YAGNI & KISS**: build what is needed now. No speculative options, flags, abstractions or
  fallbacks, no backward compatibility, delete dead code (Git is in place).
- **No story-telling in source.** Code, workflows, Makefiles and LaTeX describe what *is*, never how
  it got there. History, earlier versions, review findings and the reason for a change go in the
  commit message and PR. Comments like these are wrong, wherever they appear:
  - "one at a time again"
  - "would be mangled by the old template engine"
  - "written before validation: the one worth reading"
  - "No retry here: ..." (a note on what the code *doesn't* do only reads against the old version)
- **Comments**: default to none. Add one only where its absence invites a wrong edit: one line,
  present tense, about the code as it stands. Before committing, reread every comment in the diff and
  delete each one you can't justify that way.
- **Source stands alone**: don't reference `*.md` paths from code (they move and rot); put the
  needed rationale inline. Scripts take paths as arguments or config, never hardcoded.
- **READMEs stay short and stable**: what the thing is, how to build, run and test it. No file
  tables, file trees, function or option lists, test counts or anything else that changes with the
  code; point at `package.json`, the `Makefile` or the code instead. Describe `main`, not an unmerged
  PR.

## Repository

- `_data/`: `career.md` is the single source of career facts; `credentials/` holds certificates and
  references (originals plus extracted `.txt`). Never invent facts: CVs and website derive from here.
- `curriculum_vitae/`: two LuaLaTeX CVs (`*-cv.tex`), generated by the Node/TypeScript scripts in
  `scripts/` via the Claude API.
- `schulte-development_de/`: Jekyll website (Beautiful-Jekyll remote theme) on GitHub Pages.
- `.github/workflows/`: one workflow per area; Renovate automerges dependency updates.

## CV generation

<important if="Working in curriculum_vitae/ or on _data/career.md">
- Run everything from `curriculum_vitae/scripts` (Node version in `.nvmrc`): `npm ci`, `npm test`,
  `npm run typecheck`. `SKIP_API=true` runs without calling the paid Claude API.
- The `.tex` files are overwritten on the next regeneration: change `_data/career.md` or the prompts,
  not the generated LaTeX.
- Compile check: `lualatex -halt-on-error <file>.tex` (CI uses the same engine).
</important>

## Website

<important if="Working in schulte-development_de/">
- `make validate` (Jekyll doctor + html-proofer + `rake test`) needs local Ruby; `make docker-test`
  runs the same in Docker.
- **No third-party requests.** Every asset the browser loads must come from this origin (privacy
  promise in `privacy.md`); vendor it under `assets/vendor/`. `rake no_external` enforces this, and
  CI runs it on the production build too.
</important>

## GitHub Actions

<important if="Editing .github/workflows/">
- Each workflow starts with a `changes` job (`tj-actions/changed-files`) instead of `on.paths`, so it
  can be a required PR check. Jobs after it need `always() && ...`, because `changes` is skipped on
  `workflow_dispatch`.
- Deploying the website, committing regenerated CVs and releasing PDFs happen only on `main`.
- `curriculum_vitae/scripts` and `schulte-development_de` are separate SonarCloud projects (each has a
  `sonar-project.properties`); their quality gates fail the build.
</important>
